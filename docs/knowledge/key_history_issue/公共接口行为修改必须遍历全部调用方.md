# KP-001: 公共接口行为修改必须遍历全部调用方

## 严重级别
fatal

## 来源
通话场景下通知弹窗延迟弹出

**问题详情**：
- 严重级别：严重（Major）
- 影响范围：多个三方应用通话场景均受影响
- 出现概率：必现
- 故障恢复：无法恢复

## 问题回顾
某系统服务订阅了非标准快捷键，该订阅在历史版本会立即返回错误。某输入服务在订阅接口 `SubscribeSpecialEvent` 内部新增了失败重试逻辑（最多重试N次，每次间隔一定时间，总计最大阻塞数秒），导致该服务的非预期订阅行为被长时间阻塞，通话通知弹窗延迟弹出。

## 代码陷阱模式

**陷阱：修改公共接口的内部行为（增加重试/延时/错误码范围调整），未逐一分析所有调用方在该行为变更后的兼容性。**

此陷阱的隐蔽性在于：
1. 修改的接口本身功能正确，正常用例验证通过
2. 非预期调用方（传入了接口设计时未考虑的参数组合）的行为变化在开发自测中不易发现
3. 重试/延时逻辑在正常调用路径上无感知，只在特定参数组合下才暴露

## 高风险代码区域

### 1. 订阅接口重试逻辑
- **文件**: `service/connect_manager/src/*.cpp`
- 当前代码已限定仅对特定高优先级进程+特定按键组合启用重试，这是修复后的结果
- **风险点**: 若后续再对其他调用场景增加重试，需同样分析所有可能的调用方

### 2. 公共事件订阅重试
- **文件**: `service/account_manager/src/*.cpp`
- `SubscribeCommonEvent` 失败后通过 Timer 延迟重试
- 需评估重试期间该订阅缺失对业务的影响

### 3. 开关事件发布等待
- **文件**: `service/subscriber/src/*.cpp`
- 等待系统事件服务就绪最多数秒，期间阻塞事件发布
- 需评估所有依赖开关事件的调用方对延迟的容忍度

### 4. 客户端重连批量重订阅
- **文件**: `frameworks/proxy/event_handler/src/*.cpp`
- 重连回调中遍历所有已注册订阅并重新提交
- 批量重订阅可能造成服务端瞬时压力

## 检查规则

修改公共接口内部行为时，必须执行以下步骤：

### Step 1: 搜索所有调用点
```
grep -rn "接口名" --include="*.cpp" --include="*.h"
```
对订阅类接口的完整调用链示例：
```
InputService::SubscribeSpecialEvent()
  → InputServiceImpl::SubscribeSpecialEvent()
    → EventInputSubscribeMgr.SubscribeSpecialEvent()
      → ServiceEventHandler::SubscribeSpecialEvent()
        → ServiceConnectManager::SubscribeSpecialEvent()  ← IPC proxy层，重试逻辑可能在此
          → CoreService::SubscribeSpecialEvent()
            → ServerMessageHandler::OnSubscribeSpecialEvent()
              → EventSubscriberHandler::SubscribeSpecialEvent()
```

### Step 2: 逐一分析每个调用方
对每个调用方回答以下问题：
1. 该调用方传入的参数是否在接口设计的预期范围内？
2. 如果接口增加了重试/延时，该调用方的调用上下文能否容忍阻塞？
3. 如果错误码范围变化，该调用方的错误处理逻辑是否仍正确？

### Step 3: 识别非预期调用方
特别关注：
- 传入参数超出接口设计预期的调用方（如订阅非标准按键类型）
- 在关键时序路径上的调用方（如通话、锁屏等对延迟敏感的场景）
- 跨进程调用的调用方（通过IPC，行为更难预测）

## 正确模式

```cpp
// 正确：重试逻辑限定在特定调用方，且在接口文档中明确声明
int32_t ServiceConnectManager::SubscribeSpecialEvent(int32_t subscribeId,
    const std::shared_ptr<EventOption> option)
{
    CHKPR(option, ERR_INVALID_PARAM);
    const std::string callerName(GetCallerName());
    bool isHighPriorityCaller = (callerName == POWER_SERVICE_PROCESS &&
        option->GetFinalKey() == KEYCODE_POWER);

    if (!isHighPriorityCaller) {
        // 非高优先级调用方：直接调用，不重试，保证其他调用方不受影响
        std::lock_guard<std::mutex> guard(mutex_);
        CHKPR(serviceProxy_, INVALID_ID);
        return serviceProxy_->SubscribeSpecialEvent(subscribeId, *option);
    }

    // 仅特定高优先级调用方订阅特定按键时启用重试（因启动阶段SA启动顺序不确定）
    constexpr int32_t MAX_RETRY_COUNT = 5;
    constexpr int32_t RETRY_INTERVAL_MS = 1000;
    for (int32_t retryIndex = 0; retryIndex <= MAX_RETRY_COUNT; ++retryIndex) {
        // ...重试逻辑...
    }
}
```

## 反面模式

```cpp
// 错误：对所有调用方统一增加重试逻辑
int32_t SubscribeSpecialEvent(int32_t subscribeId, const std::shared_ptr<EventOption> option)
{
    // 不区分调用方，统一重试 → 非预期调用方被阻塞
    for (int32_t i = 0; i < MAX_RETRY; ++i) {
        ret = InternalSubscribe(subscribeId, *option);
        if (ret == RET_OK) return ret;
        sleep_for(RETRY_INTERVAL);
    }
    return ret;
}
```

## 错误码变更的关联风险

当错误码范围在不同分支中调整时，需要确保：
- 调用方判断成功的条件不会因错误码范围变化而误判
- 主干和各发布分支的错误码定义一致

相关错误码定义需关注：
- 通用返回值：`RET_OK = 0`, `RET_ERR = -1`, `RET_UNSUPPORT = -2`
- 订阅专用错误码范围：需确认各分支定义一致
- 服务端错误码：需确认各分支定义一致
